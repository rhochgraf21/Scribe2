# Scribe — browser edition

Live English captions with inline speaker labels. React, shadcn components, Atkinson Hyperlegible, ONNX Runtime Web, and local Nemotron or Moonshine speech models. No inference backend, audio uploads, recording, or transcript storage. Refresh clears the conversation and imported file references.

## Use

Open the HTTPS site in a browser with WebGPU support. Select **Download models** to fetch the pinned, approved models (about 912 MB), or select **Import models** and choose your `browser-models` folder containing `asr/` and `diar/`. Click **Load local models**, choose your microphone, then **Start captions**. Each device needs its own copy of the approved models. Import verifies exact sizes and hashes before inference. Unrelated files are ignored; missing, duplicate, or changed required files are rejected. Files are never uploaded. Downloads stream through 4 MiB integrity checks into browser storage, without holding entire model arrays in JavaScript. Block hashes were derived from the existing model files after verifying their pinned full-file hashes. Completed downloads are restored and verified on refresh; interrupted files restart, while completed files are reused. Imports remain in memory. Use **Delete saved models** to clear downloaded model data; browser storage limits or eviction may require downloading again.

Existing local installations can copy their `browser-models` folder to another device. The approved repositories, immutable revisions, filenames, and integrity hashes are in `config/browser-models.json`. Downloads begin only when you click **Download models**. Progress and cancellation are available. Download requests go to Hugging Face and its approved CDN; credentials and referrer are omitted. Models are approximately 912 MB; verification and inference need additional RAM. Smaller devices may not keep up.

WebGPU runs speech encoding and speaker detection in separate workers; they still share GPU resources. Token decoding runs on CPU. CPU-only mode is available. **CPU speech + WebGPU speakers** also supports Moonshine in one shared worker, with no silent fallback to CPU. On GitHub Pages, an app-scoped service worker adds cross-origin isolation headers and reloads once before the app starts, enabling WASM multithreading in supported browsers. If service workers or site storage are blocked, the app falls back to one CPU thread and explains the limitation in diagnostics. Speaker assignments and word boundaries are approximate. If speaker detection falls over 15 seconds behind it stops, while captions continue with a visible warning.

## Build and publish

Node 24 or newer. Install with `npm ci --ignore-scripts`, run `npm audit`, `npm test`, and `npm run build`. Serve `browser-dist` using HTTPS (localhost is also usable for development). Do not open HTML directly with `file://`.

Choose **GitHub Actions** in repository Settings → Pages. The included workflow installs locked dependencies, audits them, runs tests, builds, and publishes `browser-dist` on changes to main. Both the root and browser.html open the same app. The production bundle includes runtime and font assets, but no models or native backend.

## Privacy and security

The website and source are public. GitHub receives ordinary site/asset requests; Hugging Face receives model download requests when requested. Microphone samples and captions stay in browser memory; no analytics or telemetry is added. HTTPS and browser microphone permission are required. Imported models must match the bundled pinned manifest; this is an integrity check, not a guarantee that an ML runtime has no vulnerabilities. Dependencies are locked; run `npm audit --audit-level=high` before each deployment.

The page uses a restrictive CSP; inference workers restrict fetch to local imported models and same-origin runtime assets. Pages cannot reproduce all the custom security headers of the original local server. Do not put secrets in this repository. The JavaScript argmax uses the original joint graph, so users do not need a locally generated graph.

Third-party source licenses and provenance are in `vendor/` and `src/browser/ASR-LICENSE`. Model licenses remain those of their respective publishers; model binaries are not redistributed here.

## CPU model choice and speaker names

Choose **Nemotron 600M INT8 · CPU** before downloading/loading to use the pinned `danielbodart/nemotron-speech-600m-onnx` INT8-dynamic export. This selection forces CPU execution for both speech and speaker detection. Its combined download is about 1,040 MB; this is file size, not peak RAM. Phone performance is experimental. The original Nemotron 3.5 model remains the default. Reload the page to switch models after loading; previously downloaded files, including the shared speaker model, are reused.

For folder import, put the CPU repository's `int8-dynamic/`, `shared/`, and `config.json` inside `asr-int8/`, alongside the existing `diar/` folder. Exact revisions, file sizes, and hashes are in `config/cpu-model.json`. CPU weights originate from NVIDIA's Nemotron Speech Streaming 0.6B, distributed under CC-BY-4.0; attribution: NVIDIA (base model), Daniel Bodart (ONNX export). Model binaries are downloaded from Hugging Face, not bundled with the site.

Click or tap an inline speaker label, type a name, and save (Enter) or cancel (Escape). Naming works while listening and while text is held. Names follow speaker IDs across live caption corrections and appear in **Export text**. They are cleared with the conversation, on starting a new conversation, or on refresh; they do not identify people across sessions.

## Moonshine streaming on CPU

**Moonshine Streaming Tiny INT8 · CPU** and **Moonshine Streaming Small INT8 · CPU** use the existing ONNX Runtime Web, with no additional Moonshine WASM dependency. Tiny speech files are about 78 MB (199 MB including speakers); Small speech files are about 209 MB (329 MB including speakers). These are download sizes, not peak memory. Start with Tiny on phones; iPhone memory and speed still need device testing. Select the model before downloading or importing, then load it normally. Folder imports use `moonshine-tiny/` or `moonshine-small/` alongside `diar/`.

The MIT-licensed English exports are from [Masterx Tiny](https://huggingface.co/Masterx/moonshine-streaming-tiny-ONNX) and [Masterx Small](https://huggingface.co/Masterx/moonshine-streaming-small-ONNX), based on Moonshine AI's streaming models. Immutable revisions and full-file hashes are in `config/moonshine-models.json`; `config/moonshine-model-chunks.json` supplies the same bounded integrity checks as the other profiles. Both profiles share downloaded speaker files. Their license and manifest are included in the build's `licenses/` directory.

The shared five-graph adapter carries frontend state, encodes a bounded sliding window with 320 ms lookahead, and decodes an updated phrase about every 800 ms. A simple energy endpointer closes phrases after 600 ms of quiet; a 12-second cap bounds attention caches during continuous speech. This can affect quiet speech and words crossing a forced phrase boundary. Stop flushes the final phrase; starting again resets model state. Active phrases can revise multiple words, so speaker attribution keeps their history until completion. This export has no word alignment outputs: word times are estimated from partial hypotheses, and speaker boundaries are less precise. Diagnostics identify this and report decoder limits. Existing speaker naming and exports work with both profiles.

## Performance diagnostics

Expand **Performance diagnostics** to see configured threads, whether browser isolation allows multithreading, per-worker queued audio and compute capacity, and stage timings in milliseconds per audio second. The first/slowest encoder calls help distinguish warm-up from sustained work. Measurements are session averages; separate workers overlap, so their timings must not be summed to estimate end-to-end latency. Model file sizes and JavaScript heap sizes are not measurements of total process memory.

**Download diagnostics** exports only timing counters, configuration, and browser details—no audio, captions, or speaker names. Before loading, the CPU thread budget can be set to 1, 2, 4, 6, or 8 (bounded by reported cores and browser isolation). More threads are not guaranteed to help. Compare the same audio and allow for warm-up; refresh before changing a loaded runtime's settings. The local server provides isolation headers directly. GitHub Pages uses `isolation-worker.js` to add the headers to same-origin app responses; it does not cache responses or intercept cross-origin model downloads. Its scope is the app directory, including repository subpaths. The startup reload is guarded against loops and happens before model loading or microphone use. Deploy the complete build, including `isolation-worker.js`, and verify that diagnostics says multithreading is available.

For an explicit local benchmark build, run `SCRIBE_BROWSER_BENCHMARK=1 npm run build`. Its `browser-benchmark.html` exposes `runCpuBenchmark` for a test harness, using already verified models in browser storage. Production builds omit this entry point.

CPU mode defaults to separate workers with a 6-thread total budget: two for speech and four for speaker detection when at least six logical cores and browser multithreading are available. Smaller devices share a reduced budget; non-isolated pages use one shared thread. The pinned INT8 speech export uses fixed input dimensions to reduce runtime overhead without changing its audio chunk size or weights.

Speaker detection uses 11-frame chunks (880 ms of new audio) with four lookahead frames (320 ms), for 1.20 s of input buffering. For a temporary GPU-memory experiment, recent history defaults to 13 frames (1.04 seconds), down from 125 frames (10 seconds). On overflow, at least one chunk moves into the unchanged 264-frame speaker-identity cache. The update period is 11 frames with the default chunk size, and the FIFO remains capped at 13 frames. This is a crash-isolation test, not an accuracy-validated default. Diagnostics show the actual history length. Benchmark overrides still accept 125, 150, 200, and 264 frames with their original 42-frame overlap policy. Speech chunking, lookahead, and the speaker identity cache are unchanged.

Speaker diagnostics split the total detection time into network execution (including ONNX input/output handling), speaker-cache updates, and remaining tensor/host work. These are components of the total, not extra costs. Timing counters reset for each recording and are included in diagnostic exports.

A local 90-second comparison (the same 45-second fixture repeated twice, 2 speech + 4 speaker threads, 880 ms chunks, 16-second history) measured 71.24 s of speaker network execution versus about 25 ms of cache/tensor work. Fixing only `batch_size=1` gave no meaningful gain: 75.73 s versus 75.69 s end-to-end, with identical final captions and speaker assignments. Buffer reuse was therefore not pursued. The fixed-batch experiment remains off by default and is available to the benchmark as `speakerFixedBatch: true`; these results are not phone benchmarks or accuracy validation.

For operator-level CPU profiling, the benchmark accepts `speakerRuntimeOptions: { enableProfiling: true }`. At stop, the worker aggregates ONNX's console trace into per-operator and per-node call counts, total/max time, and totals after the first 46 model calls (about 40 seconds at the default chunk size). Trace durations are converted from microseconds to milliseconds; tensor contents are not retained. Profiling is off in normal use, and its timings must not be compared directly with unprofiled throughput. Run profiles in a fresh benchmark session.

The benchmark also accepts boolean `enableCpuMemArena` and `enableMemPattern` in `speakerRuntimeOptions`. Compare each separately and together against the same baseline, with profiling off and fresh sessions; verify captions and speaker assignments. These options affect allocations inside ONNX, distinct from the JavaScript tensor/cache timings in diagnostics. Unsupported runtime option names are rejected.

The 90-second operator profile recorded 102 speaker calls and 72,930 kernel events: `MatMulNBits` accounted for 77.1% of summed kernel time, `MatMul` 8.8%, and `BiasGelu` 3.8%. The first unprofiled comparison measured defaults 1.02×, memory arena 1.16×, memory patterns 1.12×, and both 1.10×. Repeating arena then defaults reversed the result (1.11× versus 1.14×); there was no repeatable speed gain, so both flags remain off. All final captions and speaker assignments matched across these runs. This fixture is not an accuracy evaluation, and these desktop timings do not establish phone performance.

Summarize a captured report with `node scripts/summarize-speaker-runtime.mjs /path/to/report.json`; it reports operator shares and checks that compared runs have the same workload and final output, without printing transcript text. Diagnostics display the active memory flags. In the UI, the former “Network execution” stage is now called “Model computation.”

The `accuracy_level=4` experiment uses `scripts/make-speaker-int8-activation-variant.cjs SOURCE OUTPUT` to generate a separate graph. It adds that attribute to all 127 8-bit, block-size-32 `MatMulNBits` nodes and asserts that removing those attributes recovers the original decoded graph exactly. External weights and verified browser storage are unchanged. The benchmark accepts `speakerAccuracyLevel: 4`, `speakerGraphBase64`, and its expected `speakerGraphSha256`; it checks the digest and substitutes the graph only in the in-memory benchmark file map. This override is absent from the production entry point. Level 0 uses the original graph.

On the 90-second fixture, the original ran at 1.099× realtime and level 4 at 1.072× (about 2.5% slower in this single comparison). Captions/speaker assignments matched, as did a benchmark-only FNV-1a fingerprint across 72,000 raw output values. This is consistent with fallback to the existing float computation path, not proof of which internal kernel ran. The experiment showed no benefit and was not enabled in normal use. The benchmark records the variant hash, output fingerprint, and value count for reproducibility; ordinary recordings do not compute the fingerprint.

### Table mode

Choose **Table mode** on `browser.html` to arrange 2–8 seats. Drag a seat or focus it and use the arrow keys. Tap a seat to save a name. Once captions are running, ask that person to speak alone, then confirm the detected voice. Use **Try another voice** to retry; a voice already assigned elsewhere cannot be moved implicitly. Clear an incorrect voice match before assigning it to another seat.

Choose **Follow a conversation**, then tap the people you want to follow. With nobody selected, captions show the whole group and name alerts remain enabled. With specific people selected, alerts only come from outside that selection. Only their identified captions appear in the main transcript; other and unidentified words remain in **Other conversation**. Enter your name or comma-separated nicknames for mention alerts. **Peek** and **Dismiss** preserve your selection. Long-press/right-click a matched seat (or Shift+F10 on a focused seat) to see its recent words. Rings indicate a recently captioned voice, rather than exact real-time speech activity.

Names and positions survive mode switches and session restarts in the current page. Voice matches reset with each new caption session because speaker IDs are session-local. Refresh clears the table and conversation. Recognition, attribution, and name-based alerts can miss or misidentify speech; semantic references such as “him” do not trigger alerts.

Validation: `npm test` covers filtering and mentions. From the parent workspace, `node scripts/qa-table-flow.mjs` builds a test-only fixture and checks confirmed voice matching, selection, mention previews, hold/resume, session reset, and mobile layouts in headless Chrome using controlled caption events. The fixture is excluded from production builds.

Table fullscreen hides the conversation header and reading toolbar, with small exit/stop controls remaining accessible. Mention cards and speaker badges appear with the seating diagram. Your name is shared between your own seat and mention settings; enter it once in either place.

Seat-count changes retain remaining names, voice matches, selections, and positions. A newly added seat starts unmatched; naming alone does not identify a voice. Use **Match a detected voice** to link an already-heard speaker to the correct named seat. New live matching ignores corrections to older words and requires several words with a consistent speaker ID. Own-voice and unidentified-speaker mention alerts are suppressed; match your own voice before alerts become active. The underlying diarization model can still misattribute speech.

## Phone setup and speech-only captions

Phones start with **Moonshine Streaming Tiny INT8 · CPU**, **Shared worker**, and **Identify speakers (diarization)** unchecked. If speaker detection is enabled on a phone with the WebGPU API, processing defaults to CPU speech + WebGPU speakers in one shared worker. Both models advance sequentially in that worker. Hardware WebGPU is required; choose CPU only in Settings if unavailable. CPU-only shared worker uses the available CPU thread budget; shared worker does not mean single-threaded. The speech-only download is about 79 MB; speaker files are excluded from downloads, saved-file checks, imports, and inference. Captions open directly in Reading mode in a full-window view. Speaker labels, Table mode, individual filtering, and name alerts require speaker detection; setup explains this before downloading. Enable it before loading to use those features, or refresh to change after loading. A smaller model reduces memory needs but does not guarantee realtime speed on every phone.

Table setup starts with your name, then offers two choices. **Name people in the transcript** requires clicking each speaker label, typing the person's name, and saving; the instruction remains visible while voices are unnamed. **Use voice identification** guides you through each person speaking and confirming their name.

## Speaker-model precision

When speaker detection is enabled, phones default to the upstream **Q4** export (about 83.1 MB); other devices default to original **Q8** (120.8 MB). Both are pinned to the same diarization revision. Settings offers Q4, Q4/FP16 (73.5 MB), and original Q8 (120.8 MB) before loading. All variants use verified, bounded downloads; no weights are bundled with the site. Phones still default to speech only. Changing precision after loading requires a refresh.

A 20-second desktop Chrome CPU/WASM fixture ran all three exports successfully. Instrumented WASM linear-memory allocation peaked at 125.4 MB for Q4, 150.5 MB for Q4/FP16, and 180.7 MB for Q8. These are one-fixture allocations, not full browser RAM, phone measurements, or guaranteed speed/accuracy. Q4 and Q4/FP16 are mixed precision: 93 MatMulNBits operators use 4-bit weights and 34 retain 8-bit weights. Reproduce file verification with `node scripts/verify-diar-q4f16.cjs /path/to/browser-models/diar q4`.

## On-device interruption diagnostics

Loading models starts a small localStorage diagnostic log. During loading and captioning, checkpoints are sampled and synchronously saved to localStorage every 25 ms, plus lifecycle events. There is no batching of storage writes; this high-frequency mode can affect performance. Settings → Performance diagnostics offers current/previous run downloads and deletion. Reopen the same site in the same browser after a tab failure to export the previous run before testing again. Use one Scribe tab for a diagnostic run; storage is shared between tabs on the same origin. Safari may still discard site data or the final checkpoint.

The recorder retains only the latest 960 checkpoints (roughly 24 seconds when timers keep pace; lifecycle events also occupy entries), with run settings and start time kept separately, for the current and previous runs only. It stores settings, timestamps, numeric processing metrics, audio backlog, transcript counts, observed WASM allocation, and speaker cache array sizes. It does not store audio, caption text, names, or raw error messages. Storage failures do not stop captions; an in-memory log remains downloadable. Deleting logs stops recording until models are loaded again.

WASM allocation measures observed linear-memory capacity, not resident RAM, total Safari memory, or GPU memory. Worker samples can lag while inference blocks the worker; timestamps show their age. A run lacking a final checkpoint is interrupted, not a confirmed jetsam event. Use the matching iPhone Analytics Data JetsamEvent report to establish the termination reason.

Workers also sample every 25 ms and around speech batches and speaker model execution. These measurements update the next persisted checkpoint; operations shorter than a checkpoint interval may not appear. Timer delays and the unmeasured GPU/process footprint mean even this interval cannot guarantee capturing the final allocation spike. Actual timer and write intervals can exceed 25 ms when the page or worker is busy.
